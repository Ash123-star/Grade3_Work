# 前言 Prelude

当前，某公司因发展需要，计划构建一个高效的任务分发、信息收集和数据分析系统，内部项目代号为** Project: Pandora**，目标为帮助公司管理层及员工实时掌握个人与团队工作情况**。**请根据甲方需求（[智能掌上日志系统\-潘多拉\.pdf](https://miroakd8hk9.feishu.cn/file/KlIBbbYvfofPiexlRxqc8t1DnFb)），搭建Android移动端App及对应的Web管理端。

# **项目任务描述**

## 基本要求

- 自由组队，每组**4\-5**人。全体成员对产品质量共同负责，同时须保留可核验的个人贡献记录

- 项目须有清晰的MVP（最小可用产品）和可选附加功能。产品应包含**至少20个彼此关联的核心用户故事**，能够形成完整业务闭环（项目范围过大、无法在各Sprint验收会被要求缩减或调整）

- 需求应说明功能需求和质量属性。至少选择并落实**2项**与项目相关的非功能需求，例如安全、性能、可靠性、易用性、无障碍、隐私或可维护性

- 基于**敏捷过程开发**，每个Sprint都必须交付一个可演示、可运行的产品增量

## 项目协作规则

- 使用**GitHub/Gitee**协作，提交历史、分支、Issue、看板和OpenSpec文件均为过程考核证据

- 使用**Pull Request**协作，除紧急修复外，合并前应至少有一位非作者成员审阅，审阅意见及修改记录保留在Git平台中

- 在当前AI开发的大环境下，本次实训要求使用**OpenSpec**框架实践基于规范驱动的软件开发。每组须在项目启动期初始化OpenSpec，并将生成的 openspec/ 及相关AI工作流文件\(proposal\-\>specs\-\>design\-\>tasks\.md等\)一并提交版本控制

- 使用**飞书多维表格/CodeArts**进行项目管理，看板中任务应能对应到Sprint和OpenSpec的change/task

- **每周五**课上每组需进行一次简短进展汇报，并产出工作周报，写明已完成工作、下一步和存在问题

- **每周三**前每组**可与**甲方（任课教师）约一次课外项目讨论（限时15分钟）

### **Sprint 0（第1\-3周）**

- 至少需要说明Epics/Key Features，即大型用户需求或核心功能，应形成如下层级：

```Plain Text
Epic（业务目标）：在线购物平台
    ├── Feature（功能模块）：用户管理
    │      ├── User Story（用户需求）：用户注册
    │      ├── User Story：用户登录
    ├── Feature：订单管理
           ├── User Story：下单
           ├── User Story：支付
```

- 每个用户故事应确定其优先级、验收标准；每个核心能力至少写出正常场景，以及必要的异常/边界场景。拆分后的用户故事、接口定义、数据约束等可嵌入OpenSpec规格中

- 技术架构应服务于实际产品，建议采用三层架构/微服务架构。应说明主要组件、外部依赖等，并进行数据库设计，确定表结构

### **Sprint 1（第4\-6周）**

- 项目应具备合理的仓库结构

- 需求变更必须通过**同步**新增或修改管理工具及OpenSpec change记录，不得只改代码而不更新规格

- （可选\&加分项）基于微服务的容器化部署，网页端使用公网链接访问

- （可选\&加分项）配置自动化流水线CI/CD，在提交或PR时执行构建和自动化测试

### **Sprint 2\-3（第7\-9、10\-14周）**

> 持续进行项目开发
> 
> 

**开发要求：**

- 更新Backlog（需求待办列表）中上一个Sprint中尚未完成的User Stories、新出现的需求或变更

- 之前已经估算过的Story优先级/工作量，可以根据你们从前面Sprint中获得的经验进行**重新估算**

**测试要求：**

- 对核心业务逻辑进行单元测试，覆盖正常、边界和异常输入

- 至少覆盖1条核心端到端业务链路的集成或系统测试

- 对每个核心功能给出正向验收和至少一个异常/无效输入验证

- 对已选的每项非功能需求给出适当证据，例如性能测量、安全检查、可用性/无障碍检查、可靠性或隐私审查

- 缺陷使用Issue或等价记录管理，至少记录现象、复现条件、优先级、处理状态和关联提交/change

- OpenSpec change中的任务完成**不等于**功能合格，必须有实际运行或验收测试等证据支撑

# 最终验收与评分

## 项目展示 Demo Day

> 一点小建议：
> 
> - 请用简洁的文字传达有信息量的内容
> 
> - 展示中请善用图表、截图等视觉元素
> 
> 

每组**12分钟**展示（10分钟产品展示 \+ 2分钟问答），展示应覆盖以下内容：

1. 用户问题、目标用户、产品价值

2. 关键架构/技术决策设计

3. 完整核心用户场景展示

4. OpenSpec中一个代表性change如何从规格、任务走到实现、测试和归档

5. 测试工作结论

6. 项目总结包括但不限于：已知问题、开发过程中的亮点操作等

## 评分维度（100 分）

> 小组成果为共同基础分，任课教师将结合Git记录、项目管理看板、OpenSpec tasks、PR审阅、Sprint周报记录及答辩情况进行调整
> 
>

|生成式软件开发（工具使用）|10|change链路完整、规格可验收、任务可追踪、归档后规格与产品一致|
