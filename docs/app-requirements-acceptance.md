## 1. 用途、来源与文档职责

本文件是两轮 APP 需求调整的统一验收入口，用于需求对齐、合并回归和发版签收。已有文档分别承载单项设计、接口和历史运行结果，不能单独覆盖本次跨首页、任务、组织选择、日志、月历及审核的验收，因此新增这一长期维护入口；后续原位更新，不按日期、会话或发布批次复制文档，不新建 OpenSpec change。

- **R1**：用户提供的第一次需求修改截图，按成员 A–E 的具体工作编号引用为 `R1-A①` 等。截图是需求来源，不作为新的仓库权限或目录分工规则；实际负责人在 Issue 中指定。
- **R2**：第二次文字需求，按五项引用为 `R2-1` 至 `R2-5`。与 R1 冲突时，以 R2 为准；未冲突的 R1 要求继续验收。
- **C1–C3**：2026-11-05 用户进一步明确：任务管理列表显示真实完成情况、派发表单不显示；公司月历恢复五行及剩余数量折叠；人员选择器使用同页可展开目录。这三项覆盖仓库此前相反要求。
- 产品规则唯一入口为 [方案](../方案.md)，候选规格与实施任务位于既有 OpenSpec；本文件维护用例和判定门槛。[统一验证入口](backend-validation.md)维护实际结果，[接口文档](backend-interface.md)维护实际契约，不能拿目标需求冒充已提供接口。
- 验收设计已转入实施与复验阶段，用例结论按第5节记录到既有Issue。指定提交 `4a1885fd1833f2073903095879b5f616ffc78ef5` 的完整树不含近三天分区或完成情况列；相关实现实际存在另一工作树未提交修改中，本批只读参考后补齐，不能据此认定该SHA在合并时被丢失。
- “下周五前发版”是客户原文，原消息发送日期未提供。若以本次沟通日 2026-11-05 为起点，对应 2026-11-13（周五）；具体截止时间、发布渠道与签收人仍须在发布 Issue 确认，不能推定原消息也发表于今天。

## 3. 执行前置条件与统一证据

使用隔离测试环境及合成账号，不向业务库灌入验收数据。执行人先在已有发布/验收 Issue 记录：需求版本、客户端和后端完整 SHA、PR、安装包版本与 SHA-256、API 环境标识、部署 JAR SHA-256、Flyway 版本/校验结果、功能开关、设备/Android 版本、字体倍率、执行人与时间。客户端必须 `USE_MOCK=false`；不把 Flutter Web 或桌面宿主替代 Android 安装验收。

准备以下可复用数据，记录真实对象 ID 与预期数量，但不得提交口令、令牌或个人资料：

| 数据组 | 必备内容 |
| --- | --- |
| 身份与范围 | 两个公司；本公司管理员、三名有效创始人、部门负责人、团队长、普通员工甲/乙/丙、待确认和停用账号；至少两个部门及各自团队、同名不同组织人员；直属关系可控 |
| 任务 | 甲乙共同参与、甲派发并参与、甲派发但不参与、仅下属参与、跨公司、待审创建；本人正式参与任务至少31条，跨过当前完整列表一页；含不同真实流转阶段、长标题、零/一/多标签、多参与人 |
| 日历 | 同日0、1、4、5、6、10条任务；跨周/跨月/跨年及合法闰日任务；带开始时间和仅截止时间任务；已知版本及竞争更新；有来源的节假日、长名称、过期缓存及上游失败 |
| 日志 | 以上海可控业务日T为今天，准备T、T−1、T−2和更早日期；草稿、已提交、无数据和失败；首次提交23小时59分59秒及24小时边界 |
| todo | 两名员工各自独立事项，空日、完成/未完成、多页、跨年及闰日；客户端与数据库记录数量可比对 |
| 审核与升级 | 一名/多名创始人配置、正常/缺失/失效直属上级、历史待审和已决定记录、双客户端并发；保留既有迁移和业务数据的升级副本 |

所有用例包含以下通用判据：加载、空、错误分开；失败不回退 Mock 或假成功；身份切换丢弃旧响应；越权不能靠隐藏按钮代替服务端拒绝；未生效候选不能显示为正式业务结果。用例优先级均为本轮发布必验，只有经用户明确缩减范围并写入发布 Issue 后才能移出，不能由开发者自行降级。

证据代号：**UI**＝Android 截图/录屏及步骤；**HTTP**＝脱敏请求/响应、身份角色及 traceId；**DB**＝隔离环境的对象版本、关系、审核/审计/outbox只读核对；**AUTO**＝测试名、命令、退出码及日志。每行必须能追溯到以上同一组版本。截图只证明画面，不能替代持久化或权限证据。

## 5. 合并保真与发版门槛

### 5.1 三阶段检查

1. **合并前确认需求和差异**：按 [Git比较流程](development-workflow.md#pr-的-git-比较基线) 记录目标分支、merge-base、head及更新PR时的previous head完整SHA，审阅完整差异和增量。将上述用例ID关联现有Issue/PR及相关文件、测试，不以提交标题代替实现。冲突处理必须核对被保留/删除的行为，特别是首页组合、Repository绑定、标签集合、审核路由、月历布局和迁移编号。
2. **合并后重新验收**：使用实际合并提交建立干净构建，核对“路由→页面→真实Repository→Controller/应用服务→数据库”的调用链。检查功能开关、mock条件、旧组件引用、资源及构建参数；即使实现文件仍存在，未接入调用链也判失败。集中执行相关自动化及本文件真实链路；分支上通过不自动继承到合并结果。合并后再改业务代码时，重验受影响用例及其跨模块链路。
3. **实际安装包验收**：从最终候选提交构建，记录APK哈希并安装核对版本、API环境；不要只检查电脑源码或旧包。最少完整走通“甲派给甲乙→独立审核→甲乙看板读取”“移动→待审原位→批准→两端刷新”“todo创建→重登→完成→恢复→删除”“多标签/树选择→保存→审核→回显”。再执行各自越权、失败、版本冲突场景。后端与客户端版本不一致时先判环境阻塞，不猜测是合并回退。

需要定位失败时，在隔离环境对已知可用提交与合并提交使用相同数据、参数和步骤比较；查明是代码/契约回退、配置/旧包、数据、需求口径或环境问题。在同一缺陷Issue记录根因及修复SHA，不直接覆盖用户工作区或回滚业务库。
