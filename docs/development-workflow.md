# 项目开发与协作流程

本文档把课程实训要求转化为可执行的组内开发规约，适用于需求分析、AI 辅助开发、代码协作、测试验收和最终交付。

## 一、开发阶段门

每项功能按以下阶段推进：

```text
需求澄清 → 当前代码调查 → 技术路线比较 → 设计确认
    → OpenSpec change → 实现与测试 → PR 审阅
    → 验收与记录 → 归档
```

高风险信息缺失时，必须先提问。高风险信息包括角色和权限、数据范围、数据库变化、公共接口、状态流转、外部服务、兼容性和验收条件。低风险命名或文案可以采用项目默认值，但必须记录假设。

每次开发开始前，开发者或 AI 必须报告：当前分支和工作区状态、相关模块和测试、已实现与未实现内容、计划修改文件、明确不修改的范围、验证方式。

## 二、需求和用户故事

项目至少维护 20 个相互关联的核心用户故事，形成可演示业务闭环。用户故事采用：

```text
作为 [角色]，我希望 [行为]，以便 [价值]。
优先级：MVP / Should / Could
前置条件：
验收标准：
异常和边界：
关联 Issue：
关联 OpenSpec：
```

每个核心故事至少包含一个正常场景和一个异常或边界场景。Backlog 必须记录优先级、估算、所属 Sprint、负责人、状态和关联 change/task。Sprint 复盘后可以重新估算，但必须保留变更原因。

## 三、架构和设计评审

涉及新模块、公共接口、数据库、权限或外部服务时，必须先提交设计说明。设计至少覆盖：

- 功能边界和明确非目标；
- 角色、数据范围和安全约束；
- 模块职责和依赖方向；
- 数据实体、索引、迁移和回滚；
- API 请求、响应、错误码、版本和幂等；
- 状态机、事务、并发、重试和失败降级；
- 技术路线候选、比较维度和推荐方案；
- 单元、集成、系统和非功能测试方案。

架构设计应服务于当前产品规模。优先选择可验证、可维护、与现有技术栈一致的方案；不得为了“看起来先进”引入无必要的微服务、队列或新数据库。

## 四、OpenSpec 流程

新能力或重大变更必须创建 OpenSpec change：

1. `proposal.md`：为什么做、做什么、影响什么；
2. `design.md`：架构、数据流、依赖、迁移和风险；
3. `specs/.../spec.md`：可验收规格和 WHEN/THEN 场景；
4. `tasks.md`：可实施、可验证、可追踪的任务。

实施前运行：

```powershell
openspec.cmd validate --all --strict
```

任务可以根据依赖、风险和验证方式批量实施，不要求每次只处理一个 task。批量实施时必须说明批次包含的 task、共同验收条件、允许修改文件和排除范围。相互依赖、风险不同、涉及数据库/权限/外部副作用或难以定位失败的任务应拆开。

只有实际代码接入调用路径并通过对应验证后，才能勾选 task。变更归档前，必须确认主规范、产品文档和实现一致。

## 五、Git 分支与提交

默认分支只通过 PR 合并。推荐分支：

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 功能 | `feature/<issue-id>-<name>` | `feature/42-log-review` |
| 修复 | `fix/<issue-id>-<name>` | `fix/57-task-scope` |
| AI/自动化 | `codex/<change-id>` | `codex/log-review` |
| 文档/维护 | `chore/<name>` | `chore/update-docs` |

每个功能或缺陷必须有 Issue。提交应小而可回滚，标题简洁、使用祈使句并说明目的：

```text
feat: 增加日报审核接口
fix: 修复任务越权读取
test: 增加日报提交集成测试
docs: 更新部署验证说明
```

提交前检查：

```powershell
git status --short
git diff --check
git diff --stat
```

发现不属于本次工作的用户改动、密钥、环境文件、构建产物或临时文件时，停止提交并先处理边界。

## 六、功能完成后的自动 Push 和 PR

当一个功能的代码、文档和测试已经完成，且相关验证通过后，AI 应自动执行以下流程：

1. 检查工作区和差异，确认只包含本次功能；
2. 运行需求对应的测试、构建和规范校验；
3. 创建一个简洁提交；
4. 推送当前工作分支到远程；
5. 创建或更新对应 PR；
6. 在 PR 正文中写入验收证据和未完成风险。

自动 Push 不是“代码写完就推送”。测试未通过、工作区混入无关修改、远程认证失败或需求仍有未实现部分时，不得伪造成功；应报告阻塞并保留本地状态。涉及分支保护、强制覆盖、删除分支或破坏性远程操作时必须停止并请求用户确认。

### PR 标题

标题用简洁语言概括单一主题，不写“更新代码”“完成开发”“优化项目”等空泛描述。

```text
feat: 完成日报提交与分层审核
fix: 修复员工读取下属日志
refactor: 拆分任务模块应用服务
docs: 补充后端部署和接口说明
```

### PR 正文

正文必须按以下标题分点填写：

```markdown
## 修改功能
- 实现了什么行为
- 关联 OpenSpec change/task：

## 设计与影响
- 涉及模块、接口、数据库、配置和兼容性变化

## 验证结果
- `命令`：结果
- 正向验收：
- 异常/边界验收：
- 非功能需求验证（适用时）：

## Issue
- Closes #123

## 未完成与风险
- 尚未实现：
- 未验证：
- 外部环境限制、回滚或兼容性风险：
```

除紧急修复外，合并前必须有至少一名非作者成员审阅。审阅意见、修改记录和最终结论保留在 GitHub/Gitee。紧急修复合并后 24 小时内补齐 Issue、测试、PR 说明和复盘。

## 七、测试和验收记录

每个核心功能必须记录：

- 正常流程；
- 至少一个异常或无效输入；
- 权限边界；
- 数据一致性或并发行为（适用时）；
- 关联测试命令、结果和运行环境。

课程要求的最低证据：

- 核心业务逻辑单元测试，覆盖正常、边界和异常输入；
- 至少一条端到端核心链路的集成或系统测试；
- 每个核心功能的正向和异常验收；
- 至少两项非功能需求验证，例如安全、性能、可靠性、隐私、易用性或可维护性；
- 缺陷 Issue 记录现象、复现条件、优先级、处理状态和关联提交/change。

## 八、Sprint 和交付

每个 Sprint 必须交付一个可运行、可演示的产品增量：

- Sprint 0：需求、MVP、用户故事、架构、数据库、流程、原型、OpenSpec 和看板；
- Sprint 1：至少一条从入口到业务/数据层的完整 MVP 链路；
- Sprint 2：核心功能增量、模块协作、接口/设计变更和测试报告；
- Sprint 3：缺陷处置、功能/集成/系统测试、两项非功能验证和完整文档；
- Final Release：可运行系统、全部 change 归档、当前规格一致、测试报告和展示材料。

每周五更新工作周报，写明完成工作、下一步、问题、风险、验证证据和个人贡献。每周更新 Backlog，保留未完成故事和重新估算原因。

## 九、禁止事项和完成度口径

以下情况不得报告为功能完成：

- 只创建接口、包结构、文档或 Mock；
- 只通过编译或静态检查；
- 只实现前端展示而未接通业务/数据层；
- 只实现正常路径而未验证权限和异常路径；
- OpenSpec task 已勾选但没有运行验收证据；
- 测试未运行却声称测试通过；
- 外部服务或生产环境未验证却声称生产可用。

所有报告必须区分：已实现、已验证、未验证、未实现、假设、风险和环境阻塞。
