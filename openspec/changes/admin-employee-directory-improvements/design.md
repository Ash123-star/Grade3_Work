# 设计

沿用 `users.team_id`、`reporting_relations`；身份证号由 `V35__employee_identity_card.sql` 新增 nullable 列及唯一索引，性别沿用 `users.gender`。当前远端主分支和组员公开分支尚无身份证号迁移，后续组员变更若出现须先对齐列名和迁移序号。管理员创建用例在同一事务内校验部门、组和同部门团队长及以上上级后写用户、角色、汇报关系和审计。目录 SQL 在公司范围内关联团队与上级，并对部门筛选在服务端验证；身份证号仅返回存在标记。Web 管理员修改复用既有领域验证与最终应用器，在事务中直接应用并审计；待确认账号启用时旧待审成员申请标记为已处理。历史成员申请若目标版本失效则详情提示当前版本并引导管理员直接确认。公司事项页面隐藏内部排序、展示设置和版本字段，提交时保留原值和内部版本。

备选方案是新增单独的管理表或客户端筛选；会复制既有组织数据或使分页统计错误，因此不采用。另一个方案是移除整个系统审核，会影响手机端和普通员工权限；按用户确认，仅 Web 管理员的操作走直接生效，其他入口继续使用现有审核。

2026-11-18 补充：年龄不新增持久化字段。Web 目录内部读取身份证号，服务端按中国时区当天和证件出生日期计算周岁，在响应前移除完整号码；无证件时回退现有 `users.age`。编辑表单随新输入的证件号即时计算年龄，保存时不传年龄，避免与手机端已存在的可编辑年龄形成两个写入来源。身份证号/性别补录等待手机端组员的数据模型及授权数据，当前 CSV 无这两列，不根据姓名猜性别或生成真实身份号码。

“申请与审核”改为当前待办而非历史列表：复用原审核可见范围，只返回 PENDING；成员确认还要求目标账号仍为 PENDING 且员工版本等于申请目标版本。已决和失效旧申请保留在数据库供审计，Web 管理员直接修改继续写“修改记录”而不产生申请。备选方案是删除 `review_requests` 历史，会破坏任务审核与追溯，因此不采用。
