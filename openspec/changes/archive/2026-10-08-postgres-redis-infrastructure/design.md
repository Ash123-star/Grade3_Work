## Context

产品基线采用 Spring Boot、PostgreSQL、Redis，当前尚无服务端工程。本变更交付可运行的数据基础，前端仍使用已有演示数据。导航约定以 AGENTS.md 为准。

## Goals / Non-Goals

**Goals:** 建立核心业务表、基础组织和权限种子；集中分段 SQL 并合成单文件迁移；PostgreSQL 与 Redis 独立打包；启动容器并验证事务、重复执行和持久化。

**Non-Goals:** 不实现登录、管理员密码初始化、业务 API、审批路由或 DeepSeek 调用；不将初始产品的其他待实施任务标为完成。

## Decisions

1. PostgreSQL 16 和 Redis 7 采用两个独立容器，同一 Compose 网络及独立具名卷。复用本机已有官方镜像，数据库端口绑定 127.0.0.1:55432 和 56379。合并两个进程到一个容器会增加健康检查和持久化管理成本。
2. `deploy/postgresql/sql/` 按编号维护 SQL；构建脚本合成 `deploy/postgresql/migrations/V001__initial_schema.sql`，输出一个 psql 可直接执行的文件。事务、advisory lock、版本及 SHA256 校验确保重跑跳过、同版本内容变更拒绝、失败全部回滚。后续结构升级使用新版本，不能改写已应用版本。
3. 业务表包含 company_id；关联使用 company_id + id 组合外键阻止跨公司关联。用户默认 pending、关联员工角色；角色授予、范围鉴权、停用会话撤销由后续服务端实现。手机号全局唯一；组织关系防循环；私人备注与日志草稿独立存储语义。默认种子只有公司、三个部门、角色和权限，没有公开默认管理员。
4. 审核保存候选 JSON、base_version、审核步骤和审计记录，数据库拒绝自审；审核生效及并发版本校验由后续服务端事务实施。任务主负责人单列、协作者独立表，流转由事件表记录，派发 UI 不新增完成情况。每日一份主日志，已提交修订由版本表承载。
5. Android/Web 后续共用服务端 API 和同一数据库；这里仅交付数据契约，不能称为双端已接通。AI 表只存作业、来源和建议；DeepSeek 密钥仍由未来服务端环境变量提供，不入库或进入客户端。
6. Redis 使用密码、AOF everysec、具名卷和健康检查；密码通过私有本地环境文件生成，不进入 ZIP、Git 或输出。Redis 用于缓存、限流和临时会话，正式业务事实保存在 PostgreSQL。打包内容含各自配置、说明、脚本；总 Compose 留在 deploy 根目录。

## Risks / Trade-offs

- [基础模型尚无完整应用鉴权] → 组合外键覆盖租户关联，文档明确 API 鉴权仍待实现，不宣称数据库提供完整 RBAC。
- [本地容器身份拥有数据库管理权限] → 仅本机绑定；正式上线需要单独应用角色、TLS、备份与网络配置。
- [修改已迁移 SQL] → 版本校验拒绝漂移；新增 V002 后演进，已有数据不自动清除。
- [部署异常] → 脚本非零退出；事务失败不留下部分业务表；容器卷保留，停止服务不删除数据。

## Migration Plan

先生成配置及包，启动 PostgreSQL，等待健康，显式执行单文件迁移；再启动 Redis 并运行验证。再次启动检查迁移跳过；重启容器验证数据持久化。上线已有数据库前先备份，本初始化不支持自动破坏性降级；回滚应用后保留新增数据，必要时从备份恢复。

## Open Questions

管理员首登改密、服务端受限账号、完整 API 范围鉴权和未来迁移编排属于后续服务端变更。
