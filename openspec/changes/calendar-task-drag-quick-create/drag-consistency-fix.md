# C-08：长任务落点与月历限流修复

优先级 P0，Issue #58。用户反馈确认框新起止日期不符合落点，连续拖动后出现 429 导致月视图不可用。

边界：保持以实际抓取日为锚点、整段时长不变及现有权限／审核／版本规则；只修正客户端预览、松手提交和读取调度，不改变后端限流阈值、接口或数据库。

选择：直接改为“手指落点就是任务开始日”会破坏中间日／跨周续段锚点规则，扩大服务器限流也会掩盖重复请求。采用最后已展示的落点快照贯通预览和确认，并在格子上标示整个候选区间；月历读取短时有界复用、合并通知刷新、使用 100 条分页以及尊重 429 冷却时间。

架构：拖拽控制器维护不可变的展示／释放快照，展示层只呈现同一候选；日期格显示候选范围和抓取日映射。月历 Provider 按会话／成员／月份隔离并有限保留成功结果；读取器维持分页完整性、并发预算及按 Repository 隔离的限流冷却；通知公共入口统一刷新，界面监听只取消旧手势和核对已有申请。

实施和运行证据见 [verification-drop-consistency.md](verification-drop-consistency.md)。通知监听在挂载期间保持稳定，避免月历重建引起断连／重连；429 冷却同时阻断其他在途月份的后续页。

验收：
- 长任务从中间日或续段抓起，跨周／跨月的高亮区间、新日期提示和确认框完全一致；最后一帧之后的松手坐标／滚动不能悄悄改变候选日期。
- 零位移、无效落点、离开月历、取消及权限失效不发改期；时长与原非日期字段保持。
- 反复翻到刚访问过的月份不重新读取所有页；通知突发不触发界面第二轮全局刷新；分页尽量使用服务端允许的 100 条。
- 月历收到 429 后遵守 Retry-After，缺失时等待 60 秒；重试按钮在冷却期不能反复发请求，冷却后可恢复。上次完整月数据可以只读显示，鉴权失败不能保留受保护数据。
- 覆盖可靠性（日期一致、无写入／无重复读）和安全（跨账号缓存隔离、失权不回退旧数据）。全仓／实机历史验收缺口独立保留。
