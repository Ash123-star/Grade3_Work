## Context

空仓库从零规划。Android 按指定五栏和四象限实现，Web 使用独立布局；详细业务见根目录方案.md。

## Goals / Non-Goals

目标：同一权限模型支持双端；日志与任务可闭环；管理者按范围穿透；DeepSeek 只提供需确认的建议。
首期不含跨公司自动联系、离线厂商推送和 AI 自动决策。

## Decisions

1. Flutter Android + Vue 3 Web + Spring Boot 模块化单体，共用 OpenAPI，减少跨端分叉。
2. PostgreSQL 持久化、Redis 缓存与限流；company_id 隔离先于组织数据范围。
3. RBAC 与组织树共同鉴权，后端过滤所有列表、详情、统计、导出和 AI 上下文。
4. 关键修改使用候选版本与审批链；申请人不可自审，无独立复核人保持待审。首次初始化单独审计。
5. 派发界面删除完成情况，后台任务事件支持反馈和验收，报表按事件计算。
6. 日志以用户+业务日期唯一，UTC 存储时间；按 Asia/Shanghai 和周一起算日周月区间。
7. DeepSeek 密钥只在环境变量，模型输出先校验并作为草稿；服务端选取权限内最小数据，超时失败不阻塞基础流程。
8. 通知采用事务 outbox、幂等事件和站内未读计数；Flutter 离线草稿提交时检查服务端版本。
9. OpenMoji 自托管并记录来源、版本及 CC BY-SA 4.0 许可，不使用图片热链。

## Risks / Trade-offs

- 反向排列底栏不常见，但遵守明确需求并默认选择最右导图。
- 初期组织人员不足可能无法独立复核，正式使用前配置至少两名可独立审核人员。
- 地图在小屏易拥挤，提供卡片列表和图切换，不依赖拖拽完成操作。
- AI 可能生成错误摘要，必须保留来源、支持编辑和用户确认。
- 组织变化和审核并发通过版本校验、即时范围重算及集成测试验证。

## Migration Plan

先创建版本化数据库迁移、三个部门和幂等管理员初始化，再实现基础闭环；之后启用审批、消息、Web 和 AI。首期无历史数据迁移。数据库备份恢复和发布回滚在 deploy 文档说明。

## Open Questions

短信服务商、部署域名和正式组织人员在上线配置阶段确定，不阻塞规范和本地基础开发。当前默认单公司、Asia/Shanghai、周一起算。
