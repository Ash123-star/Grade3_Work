# Design

## 当前用户确认增量（覆盖下文旧批次的视觉冻结约束）

用户已确认按[现有原型](../../../mobile/prototypes/home-daily-todos.html)实施 Flutter 人员目录：选择器左侧头像、右侧姓名，目录名称左侧只有展开箭头，不使用文件夹图标；“我的 → 人员展示”只加入部门→团队同页展开，原 `_PersonnelCard` 的头像、姓名、部门、参与任务数、日志状态、未结束任务状态和点击路由全部复用。接口、资格、分页、会话隔离和其他页面不变。

采用共用原生目录节点和组织ID分组，选择器保留独立选中集合与原HTTP加载；相比新增目录页面或新接口，此方案没有迁移成本，不改变权限，可独立回滚。无匹配、请求失败、头像缺失和统计未知继续显式反馈；320宽/1.5倍字体及键盘操作需验收。关联现有 Issue #53，本批不新建 change。

## Context

参见 [proposal.md](proposal.md)。当前 `GET /api/organization` 已返回授权范围的部门、团队和人员，`GET /api/organization/people` 已支持姓名/部门搜索与分页，但选择器契约没有明确路径与可选资格。任务标签关联表以 `task_id` 为主键，当前只允许单标签；年度场景的 `db/scenario` 迁移仅创建一名 `scenario-founder`。

## Goals / Non-Goals

**Goals:**

- 将组织目录响应定义为可供既有人员选择器直接使用的数据契约，服务端作为权限和选择资格的唯一判断点。
- 将标签关系升级为每任务零到多条，保持任务创建、修订审核和读取投影的一致性。
- 使用增量场景迁移加入多名虚构创始人，覆盖多账户测试而不改变任何审核策略。
- 保持现有 Flutter/Web 视觉风格不变。

**Non-Goals:**

- 不重做 Flutter 页面、视觉 token、导航或交互样式；目录编排仅调整为已确认的同页展开方式。
- 不改变多创始人审核路由、创始人免审规则、管理员成员确认或通知投递。
- 不修改已发布 Flyway 迁移；不把场景数据迁移当作生产业务迁移。

## Decisions

### 1. 复用组织目录接口而非新增平行人员树

推荐在现有组织树/人员查询契约中补齐 `departmentId`、`department`、`teamId`、`teamName`、`status`、`role` 和可选资格语义，并使搜索结果带完整路径。现有前端仅用这些字段展开既有目录和保持选中状态，不调整组件样式。

备选方案是新增独立 `/organization/person-picker` 接口。它会产生重复的范围查询、缓存和错误模型，且需要前端维护两套目录；因此不采用。

### 2. 多标签采用关联表集合与增量 Flyway 迁移

实施时由任务模块将请求/响应字段从 `labelId` 过渡为 `labelIds`/`labels`。新增的 server Flyway 迁移须先删除 `task_label_links` 的单任务主键或唯一约束，改为 `(task_id,label_id)` 联合唯一约束，并保留公司范围与标签查询索引。旧任务的一条关联记录自然兼容为单元素集合；旧客户端的 `labelId` 仅在明确兼容窗口内转换为单元素集合，不能与 `labelIds` 同时产生歧义。

在同一审核生效事务中，先验证全部标签均为当前公司、ACTIVE 且对申请人可见，再整体替换关联集合与任务正文投影；任何一个标签无效则整项候选不生效。读取端按稳定顺序返回 `labels`（含服务端颜色）。任务管理列表通过授权投影中的只读 `phase` 展示真实完成情况，映射及兼容规则见 [接口契约](../../../docs/backend-interface.md)；未生效候选不覆盖正式流转，缺失或未知值显示“情况未知”。派发表单仍不得显示、提交完成情况或替代状态字段。

备选方案是把多个标签序列化到任务 JSON。该方案难以建立外键、范围过滤和索引，也会与当前关联表冲突，因此不采用。

### 3. 多创始人使用独立场景增量数据

在当前年度 `server/src/main/resources/db/scenario-annual2026/` 新增下一版本的场景迁移（实施时根据当前最高版本确定文件名），插入至少两名 `annual-` 前缀的 ACTIVE FOUNDER 账户、对应角色记录以及少量可辨识的标签/任务关联数据。迁移必须使用事务并仅由显式 `annual-2026` 场景 bootstrap 执行；旧 `db/scenario` 已标记为 legacy，不在本变更写入。

不修改 `users.role`、审核申请或审核步骤算法；多名创始人只使现有规则被多个独立账户覆盖验证。备选方案是修改已发布的年度 `V1__annual_workplace.sql`，会破坏已发布场景迁移可重放性，因此不采用。

### 4. 职责与契约协作

本次任务清单明确成员 B 负责创建/派发任务、多标签与组织人员选择，因此成员 B 负责组织目录范围、标签集合持久化、现有 Flutter 派发表单的数据绑定、场景数据及对应测试；成员 E 负责公共 OpenAPI/文档和多创始人审核规则确认。前端改动仅限现有表单的数据、同页目录编排、搜索展开与选中状态，保持既有颜色、字体、导航和组件风格。跨模块提交前必须确定 Issue 编号、接口字段和迁移版本。

### 5. 同页可展开人员目录与字段标识

2026-11-05用户确认以同页展开覆盖此前分页式目录：人员选择器在同一面板提供部门→团队→人员目录，支持展开和收起，不切换到独立层级页面。搜索时展开命中的部门、团队路径并显示人员；跨节点选择、收起节点、搜索及清空搜索均以稳定人员 ID 保持同一选中集合，同名人员用组织路径区分。目录读取与提交仍由服务端校验公司、组织范围和人员资格，搜索失败明确提示，不用旧结果伪装成功。实现复用既有 `ListTile`、`IconButton`、`LoadingSkeleton` 与主题文字样式，只替换目录的编排方式，不引入新的视觉风格。字段标识改用市面通用的红色 `*`：必填字段在名称前显示星号，未标注即选填；不改变字号、颜色 token、分组和提交校验，也不在表单顶部额外增加说明行。派发页标签选择面板删除重复的“标签可不选，也可选择多个”说明。

## Risks / Trade-offs

- [任务标签迁移与其他分支迁移号冲突] → 实施前同步 `main` 并以当前最大版本后的新编号创建迁移，绝不改写 V21。
- [旧客户端只发送 `labelId`] → 在契约中设定有限兼容转换与冲突规则，并为新旧请求分别测试；最终移除窗口另行立项。
- [多创始人触发现有免审分支] → 场景测试只验证当前行为，禁止借数据迁移改变 `ReviewApplicationService` 的规则。
- [组织目录把待确认或范围外人员显示为可选] → 读取端显式标记/过滤，写入端再次校验，集成测试覆盖伪造 ID。
- [前端改动漂移为样式重构] → PR 仅接受数据层、同页目录编排、状态绑定和契约测试；无关布局、颜色、字体或导航改动单独拒绝或拆分。

## Migration Plan

1. 在合并前确认当前 `main` 的 Flyway 最高版本及相关 Issue/负责人。
2. 新增多标签结构迁移并回填/保留既有单标签关联；先在空 PostgreSQL 运行，再在含历史标签关系的升级库运行。
3. 新增独立场景增量迁移，验证重复执行/前缀冲突安全失败。
4. 发布服务端组织与任务契约后，由客户端接入数据绑定和同页目录编排，保持既有视觉样式。
5. 运行受影响单元、PostgreSQL/Redis 集成、跨端契约、越权和严格 OpenSpec 验证，记录命令、环境和结果。

Flyway 已发布迁移不可回滚或改写；若发现问题，以新的前向修复迁移恢复约束或数据投影，并从升级前备份恢复业务库。场景数据仅能在独立场景库重建，不得对生产库执行清理脚本。
