# 设计

## 路线比较

客户端逐人查询任务/日志可复用接口，但会形成N+1请求、分页计数不准且易泄露草稿。采用人员仓储在已有组织范围内执行实时聚合，在同一分页查询中返回统计；任务计数同时应用调用人的TaskAccess范围。无需持久化重复计数字段或新增框架。

## 数据与契约

- GET /tasks/received-card：沿用公司数据范围，再限定当前人参与，所有生命周期记录保留；不排除本人派发给本人的任务。分页总数与items同一条件，首页与列表共用provider。
- GET /organization/people：追加 participatingTaskCount、activeTaskCount、todayLogStatus、summaryDate；任务数按唯一任务计，active排除ACCEPTED/ARCHIVED/WITHDRAWN。日志状态SUBMITTED/MISSING/UNKNOWN；上海业务日，仅存在已提交记录才SUBMITTED，待确认UNKNOWN，不披露他人草稿。
- task events.actor_name、review steps.reviewer_name、audit.actor_name均来自同公司users.name。客户端统一缺失姓名占位，不用账号或内部ID作人名。
- 日志无独立标题字段且现有表单只编辑正文，故摘要从work首个非空行生成，移除序号并截断到48字符；不把日期当标题，无正文时“工作日志”。用户此处“角色名字”解释为姓名而非职级，后续如需职级可独立加标签，不改变账户。

## 验收矩阵与边界

用户追加要求：视图页恢复任务管理入口（保留日志页入口）；日/周/月均限定当前用户参与任务，月视图默认currentSession.id，显式成员日历保留memberId。用户授权提交并云端部署，先备份云端本地修改、JAR和数据库，再同步当前分支；只执行部署必需的跳过测试打包，不运行验收套件。

任务：多页、自己派发且参与、本人无任务/管理者有下属任务、失败重试；日志：日期与标题分离、空白/多行/多字节正文；姓名：真实姓名、缺失用户、历史审批；人员：实际0与未知区分、今日提交更新、上海跨日、待确认、跨公司与范围外任务不可计入。不记录密码/token，不修改已应用迁移。只检查当前批差异与OpenSpec，测试源码可补充但按用户指示暂不执行；构建、真实HTTP、设备交互与非功能权限/可靠性验证留待统一验收。

## 审核与通知展示修复（2026-10-30）
当前分支chore/annual-scenario-dataset，开始时工作区干净。采用后端在已授权审核详情中仅解析快照引用的同公司名称、前端格式化中文字段的路线；相较客户端拉取全公司目录，避免额外目录权限及分页依赖。before_value/candidate仍保存原始业务快照，追加display_references只供展示，不参与审核决策，无数据库迁移。名称是当前名称，不能声称历史名称；不存在的引用显示名称不可用，不显示ID。已通过/驳回/失效记录使用状态对应说明，创建申请显示首次创建而非v0当前生效。
通知沿用现有recipient_id/type/object_id契约，补齐历史TASK_DISPATCHED与生产类型中文标题和已存在详情路由；无有效目标显示明确提示，详情继续服务端鉴权。标记已读失败时允许打开详情并保留失败提示，未读状态不伪造成功。审批卡片撑满父级可用宽度，保持页面边距。
仅修改审核/通知展示、名称投影和契约文档，不更改权限、审核流程、原始快照、数据或样式体系。验收步骤：分别打开创建与修改申请及其各审核状态；核对中文字段、上海时间、标签与成员名；点击历史派发及审核通知；检查缺失目标与已读失败；长短标题及大字体下卡片等宽。安全与可靠性关注点为跨公司引用不返回名称、已读失败不阻断导航。按用户要求不运行编译、测试或设备验收；任务保持未验证。
