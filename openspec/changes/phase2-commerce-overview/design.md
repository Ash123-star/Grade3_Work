# Design

## Context

主线有 Vue 管理端、统一认证及 PostgreSQL Flyway。C 的 #104 使用 `customer_memberships.mall_member_id` 表示已确认的公司内唯一商城会员，另有独立的客户外部 ID。A 的 #105/#106 提出了 CRM 投影，真实全模块投影尚待联合验收。E 以 C 的提交 `f57725c72f21eeeaeb05cbeee119112cd033ef6e` 为实施基线。

## Goals / Non-Goals

首版覆盖每个公司一个商城标识域、文件重放、源快照更新、成员绑定查询和可对账明细。正式财务指标、商城直连、其他岗位放行与跨模块 CRM 投影依赖后续已确认契约。订单状态只用于分组，退款状态仍显示该单的原始金额。

## Decisions

- **文件与版本。** 在现有 Java 服务解析 UTF-8 JSON，可在一个文件上传互相关联的会员、订单，并在同一事务内生效。CSV 适合单表但需要双文件关联和额外的原子提交约定。商城 API 需要供应商契约与测试权限。首版接受两个数组合计最多 500 条、文件最多 1 MiB。实体以外部 ID 去重，`sourceUpdatedAt` 为源版本。相同版本相同内容忽略，旧版本忽略，同版本异内容冲突。订单会员、下单时间、币种随外部订单 ID 固定，保护原关联及汇总口径。
- **并发与溯源。** `commerce_imports` 以公司和文件 SHA-256 唯一，记录上传人、时间及批次计数。对同公司的导入锁定公司行，串行执行查重、写入和审计，数据库继续以复合唯一键和复合外键兜底。比并行逐行 upsert 更易保证跨表原子性及同批重放反馈，代价是同一家公司的大文件排队。记录只保留当前快照及对应凭据和数组序号，凭据不保留原始文件。文件只接受声明字段，错误和常规日志避免回显输入值。
- **客户关系。** E 通过 C 应用服务读取已确认的 `mall_member_id`，与 E 的 `externalMemberId` 精确关联。直接写 C 会员表或基于姓名/手机号自动合并都会绕过 C 的人工确认及版本约束。访客订单允许空会员 ID；提供外部会员 ID 时对应会员必须已导入或包含在本批。
- **权限与查询。** `/commerce` 从 Web 管理后台导航进入，也支持直接访问。商城共用后台登录、布局、导航和基础组件样式。`/api/commerce` 允许已改初始密码的 ACTIVE ADMIN，公司取自认证。C 的绑定查找继续执行 C 的公司/角色检查。汇总、列表及列表计数共用 SQL 范围，日期按上海自然日转为半开 UTC 区间，金额以 PostgreSQL NUMERIC 精确计算并按字符串返回。购物订单与既有任务/日志统计分属不同数据模型。导入业务来源为外部快照，C 主数据绑定继续沿用现有版本写入。接口契约集中于后端接口文档和 SpringDoc。
- **验收。** Docker PostgreSQL/Redis 驱动 HTTP 测试，覆盖导入、同文件并发、历史更新、事务回滚、绑定后按客户回查和权限。浏览器覆盖真实 API 主链路及异常/窄屏。三条二期联合验收仍依赖 A 的真实 CRM 投影、D 线下业务双向查找、B 合同权限与提醒。

## Risks / Trade-offs

- 商城源状态与字段由上线前转换规则确认。文件只有原始订单金额，跨币种分别呈现。
- 日期口径按下单时间；后续导入可以改变当前分组。每次钻取执行最新授权和匹配条件。
- 真实客户绑定变更会影响之后的客户投影，由 C 校验版本。跨商城复用同一个外部 ID 时需另行确认商户命名空间。

## Migration Plan

V39 新建 `commerce_imports`、`commerce_members` 和 `commerce_orders`。先确定 C #104 与 #103 的 V37 编号冲突及可能占用的 V38，再发布 E。发布前在已有主线数据库验证升级并保留备份。应用回滚可停用前端入口并还原旧 JAR，保留 V39 表与数据；已经发布的 Flyway 迁移按追加版本前进。
